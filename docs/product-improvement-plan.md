# MathWeaver 产品方案改善计划

> 基于 Bem 六维思维框架深度审计 + 产品方案薄弱环节诊断

## 核心诊断

产品方案的根问题不是某个单点薄弱，而是**三套文档互相矛盾 + 理论根基未打通 + 商业维度缺失**。

代码实现度其实不低（四场引擎 85%、Agent 编排 85%、Cayley 表 90%），但方案文档把实现描述成了一个比实际大得多的系统，反而损害了可信度。

### 2. 六维框架写入主 Proposal

**问题**：`thinking-abilities-framework.md` 是高质量理论文档，PPT 第 8 页已呈现，但主 proposal 通篇未提 Bem 六维。

**行动**：在 proposal 第 3 章"系统设计"中插入新节"3.1 理论根基：六维思维能力框架"：

```markdown
### 3.1 理论根基：六维思维能力框架

MathWeaver 的七 Agent 架构并非随意设计，而是基于 ER Bem
《数学思维能力的训练》(1985) 的六种数学思维能力映射：

| 思维能力 | Bem 的方法 | MathWeaver 组件 | 实现状态 |
|---------|----------|----------------|---------|
| 分析 | 追溯型分析法 | Proof Assistant + Socratic | v0.3 ✅ |
| 设想 | 笛卡尔万能模型 | Conjecture Engine | v0.4 规划 |
| 归纳 | 枚举→数学归纳 | Pattern Builder + Grill | v0.3 ✅ |
| 模拟 | Polya 模型论 | Concept DAG + Explorer | v0.3 ✅ |
| 类比 | 跨域结构映射 | Curriculum Mapper + Historical | v0.3 ✅ |
| 逻辑推理 | 三段论·充足理由律 | Z3 Proof Assistant | v0.3 ✅ |

第七个 Agent（Meta 元认知）对应 Bem 框架之外的"元认知自进化"能力，
负责追踪学习者的思维策略本身，不直接对应六维之一。
```

**效果**：Agent 数量从"拍脑袋"变成"理论驱动 + 1 个元认知扩展"，论证力大增。

## P1 重要级改善（本周内执行）

### 3. 重建竞品差异化

**问题**：遗漏 Brilliant.org（最直接竞品）和 Wolfram Alpha（形式化验证标杆）。

**行动**：重写 proposal 第 8 章竞品分析：

```markdown
### 8.x 与 Brilliant 的关键差异

Brilliant 已实现规模化"发现式学习"，价值主张高度重合。
MathWeaver 的差异化在于三个层面：

1. **形式化验证深度**：Brilliant 的交互练习靠预设答案判定对错；
   MathWeaver 用 Z3 逐步验证推理链，支持学习者构造自己的证明。
   → 适合需要形式化严谨的大学级抽象代数。

2. **思维过程可见性**：Brilliant 的课程是设计好的路径；
   MathWeaver 的苏格拉底 Agent 让学习者自己的思维过程外显
   （追溯型分析、猜想→反驳→修正链）。
   → 适合需要"学会怎么想"而非"学会这个知识"的用户。

3. **自适应认知诊断**：Brilliant 的难度调整基于答题正确率；
   MathWeaver 的四场耦合引擎同时追踪知识/认知/情感/交互。
   → 但此项需要用户数据验证，当前为设计论证非效果论证。
```

**关键诚实声明**：必须承认"对于 80% 的中学生，Brilliant 已经够用。MathWeaver 的目标用户是需要更深层思维训练的特定群体。"

### 4. 补全商业模式

**问题**：proposal 第 11.3 节只有 3 行"可持续性"。

**行动**：补充完整的商业模式框架：

```markdown
### 11.3 商业模式与可持续性

#### 定位：开源教育研究项目（非商业 SaaS）

MathWeaver 的核心定位是**开源教育研究项目**，不是商业 SaaS。
可持续性依赖三条路径，按优先级排序：

**路径一：学术研究合作（首要）**
- 与大学数学教育研究者合作，作为研究工具获取科研经费
- 目标：2 所合作院校，产出 1-2 篇教育技术论文
- 收入形式：科研合作经费、设备资助

**路径二：开源社区贡献（次要）**
- GitHub 开源社区贡献者维护核心框架
- Apache-2.0 核心框架 + CC BY-SA 教育内容
- 目标：50+ stars，5+ 外部贡献者
- 收入形式：开源基金会资助（如申请 EduOSF 资助）

**路径三：机构采购（探索性）**
- 大学数学系采购私有化部署用于教学辅助
- 定价：按校 2000-5000 元/年（含部署支持）
- 目标：1-2 所试点院校
- 收入形式：年费 + 部署服务费

#### 不做的事
- 不做 C 端付费（学生付费意愿低、获客成本高）
- 不做广告变现（教育场景冲突）
- 不做数据商业化（PIPL 合规风险）
```

## P2 改进级改善（迭代中执行）

### 6. 技术方案分层标注

**问题**：proposal 技术栈列出 20+ 核心依赖，但未区分"已实现 / 规划中 / 探索性"，让评委无法判断哪些是真的、哪些是愿景。

**注意**：不应该砍掉 Manim、Three.js、眼动——它们各自服务于六维框架中的特定维度。正确做法是分层标注，让方案既有诚意又不过度承诺。

**行动**：在 proposal 技术栈部分增加四态标注：

```markdown
| 技术组件 | 状态 | 六维对应 | 说明 |
|---------|------|---------|------|
| Z3-Solver | ✅ 已实现 | 逻辑推理 | 四层 Fallback L1-L2 |
| 七 Agent + Orchestrator | ✅ 已实现 | 全维度 | 单写者模式 |
| Concept DAG (193节点) | ✅ 已实现 | 模拟 | 8 课程层级 JSON |
| 四场耦合引擎 | ✅ 已实现 | 全维度 | 五种教学决策 |
| Cayley 表编辑器 | ✅ 已实现 | 模拟/逻辑 | 闭合性/结合律实时验证 |
| Grill 自适应难度 | ✅ 已实现 | 归纳 | 五 band 难度带 |
| Pattern Builder | ✅ 已实现 | 归纳 | 拖拽式模式发现 |
| Encouragement Engine | ✅ 已实现 | 全维度 | 成长型思维语言 |
| Conjecture Engine | 🔨 v0.4 规划 | 设想 | 猜想→验证→修正链 |
| 启发式验证 | 📋 仅设计 | 逻辑推理 | L3 Fallback 框架就绪 |
| Three.js 3D 对称群可视化 | 📋 规划中 | 模拟 | 正多面体对称群(S₄/A₅)需 3D 渲染，SVG 2D 不足 |
| Manim 动画管线 | 📋 规划中 | 模拟/类比 | TheoremExplainAgent 多模态讲解，让思维过程可见 |
| 眼动认知负荷增强 | 🔬 探索性 | 全维度 | 教研合作场景可选增强，不绑定硬件 |
```

**为什么保留这三项**：

- **Three.js 服务"模拟能力"**：抽象代数的正多面体对称群（S₄、A₅）天然是 3D 几何对象。
  当前 InteractiveExplorer 只有 Cayley 表（代数模型），缺几何模型。
  多模型切换（文档 5.4）需要 Three.js 渲染对称变换的 3D 可视化。
  SVG 只能做 2D 投影，对于"旋转一个正四面体看看哪些变换保持不变"不够用。

- **Manim 服务"模拟能力"+"类比能力"**：TheoremExplainAgent 管线
  （规划→编码→Manim 动画→TTS 语音）直接实现"让思维过程可见"。
  3Blue1Brown 已证明程序化数学动画在 STEM 教育中显著优于静态图形。
  当学生理解"群的生成元如何逐步生成整个群"时，动画比文字更有效。
  但需注意 Manim 是 Python 库需预渲染，不适合实时交互——
  定位为"按需生成的概念讲解动画"，而非实时响应。

- **眼动服务"四场耦合引擎"**：当前情感场用"响应时延 z-score + 跳题率"
  估计焦虑，这是弱信号。眼动追踪（注视时长、瞳孔直径）能提供更直接的
  认知负荷信号。proposal 已正确将其定位为"可选增强，不绑定硬件"。
  在学术研究合作场景（商业模式路径一）下，这是有价值的科研功能。

**效果**：评委一眼看到"哪些已实现，哪些是规划，哪些是探索"，可信度大增。
同时保留了这些技术对六维框架的覆盖，不会因为错误砍掉而出现能力缺口。

### 7. 降低"AI 味"

**问题**：文档 90% 篇幅在讲"AI 能做什么"，10% 在讲"教育会发生什么"。

**行动**：

**7.1 增加真实使用叙事**：在 proposal 中插入 1-2 个具体使用场景：

```markdown
### 场景：一个学生在 Grill 模式中的 15 分钟

小明是数学系大二学生，正在学习群论中的"循环群"概念。

0:00  打开 MathWeaver，DAG 显示"循环群"节点为 current 状态。
      四场仪表盘显示：mastery=0.45（ZPD 区域），anxiety=0.3（正常）。

0:02  Grill 模式生成题目："Z₆ 的生成元是什么？为什么？"
      小明尝试回答"2 和 3"，系统验证后标注"部分正确"。
      Socratic Agent 追问："Z₆ 中哪个元素的阶等于 6？"

0:05  小明打开 Cayley 表交互器，选择 Z₆，逐一验证每个元素的幂。
      系统实时标注：1⁶=e, 5⁶=e, 但 2³=e（阶为 3）。
      Encouragement Engine："你正在用枚举法——这正是数学家寻找
      模式的方法。"

0:10  小明发现"只有 1 和 5 的阶等于 6"，回答"生成元是 1 和 5"。
      系统确认正确，mastery 升至 0.62。
      Historical Agent："Euler 在 1761 年研究模运算时也发现了同样的
      结构——元素与其阶的关系。"

0:15  DAG 自动推荐下一节点"循环群的子群结构"。
      四场决策：in_flow + mastery>0.6 → advance。
```

**7.2 减少术语密度**：把 proposal 中每段 3-5 个英文术语降到 1-2 个，用中文解释替代缩写。

### 8. MVP 边界明确化

**问题**：代码已扩展到 8 学科，但文档还在说"初版聚焦群论"。

**行动**：明确 v0.3 的功能边界：

```markdown
### v0.3.0 功能边界

#### 已实现且可演示
- 群论核心概念 DAG（193 节点，8 课程层级）
- Cayley 表交互 + Z3 闭合性验证
- 七 Agent 苏格拉底协作
- 四场耦合认知引擎
- Grill 自适应难度（五 band）
- Pattern Builder 拖拽式发现
- Conjecture Timeline（猜想→验证→修正）

#### 数据已有但交互未完整
- 线性代数 / 数论 / 微积分 / 离散数学 DAG（仅数据，交互未 wiring）
- Curriculum Mapper 跨课程映射（前端硬编码，未与后端动态联动）

#### 刻意延后
- K-12 课程（不收集未成年人数据）
- 移动端（专注桌面体验）
- 教师仪表盘（v1.0）
- 多语言内容（UI 框架支持，内容仅中文+英文）
```

## 代码层面的六维框架补全

基于代码实现差距分析，以下是按六维框架组织的代码改进优先级：

### 分析能力（当前 70%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| 追溯型倒推视图 | P1 | 在 ProofPanel 增加"倒推模式"tab：先写结论→系统引导逐步倒推→翻转为正向证明 |
| 推理链有向图 | P2 | 用 SVG 渲染推理链图：节点=命题，边=推理+理由，断裂处红色标注 |

### 设想能力（当前 65%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| 任意 DAG 节点自由猜想 | P1 | ConjectureHandler 扩展：监听任意节点页面的"我猜…"输入，不限预置群 |
| NL→Z3 自动转译 | P2 | LLM prompt 工程：自然语言猜想 → SMT-LIB 表达式 → Z3 验证 |

### 归纳能力（当前 80%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| 枚举→数学归纳显式引导 | P2 | Grill Mode standard→advanced 过渡时，插入"你能证明这个模式对所有情况成立吗？"引导 |

### 模拟能力（当前 75%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| 多模型切换 | P2 | InteractiveExplorer 增加模型切换：代数(Cayley表)/几何(对称变换图)/拓扑(轨道图) |

### 类比能力（当前 60-70%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| 跨课程结构对照视图 | P2 | CurriculumMapper 增加"结构对照"tab：并置群同构/线性同构/拓扑同胚 |
| Historical 前端集成 | P1 | 在 ConjectureTimeline 中直接嵌入历史叙事卡片 |

### 逻辑推理能力（当前 70%）

| 缺口 | 优先级 | 实现方案 |
|------|-------|---------|
| Z3 深度集成 | P1 | ProofPanel 的每步验证从关键词匹配升级为 Z3 求解 |
| 推理链可视化 | P2 | 与分析能力共享，推理链有向图同时服务两个维度 |

## 总结：一句话改善原则

**把方案从"AI 能做什么"转向"学生会发生什么变化"。**

每一个技术组件的描述，都应该回答一个问题：这个组件让学生获得了 Bem 六维中的哪一种思维能力？如果回答不了，这个组件就是过度工程。
